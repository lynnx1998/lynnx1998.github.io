Orbit

让个人 Agent 从“替你做事”，变成你能够理解、控制与修正的长期协作者。

一个面向个人 AI Agent 的移动端产品原型。它把持续运行的自动化整理成清晰的状态、重要变化与可验证规则，让用户知道 Agent 做了什么、为什么提醒，以及改变规则后会发生什么。

01 · Context

Agent 真正的问题，不只是“会不会做”。

当自动化开始在后台持续运行，用户需要建立的不是一次性信任，而是长期的理解与控制：它现在在做什么？为什么这件事值得打断我？它拥有哪些权限？我的一句修改会造成什么后果？

01状态不可见

多个 Agent 同时运行时，聊天记录无法成为有效的控制中心。

02通知失去意义

如果每次执行都提醒，用户很快会忽略真正重要的变化。

03修改缺少预期

自然语言很方便，但在应用新规则前，用户难以判断它会如何行动。

02 · Concept

把 Agent 设计成可观察、可解释、可撤回的系统。

Orbit 不把 Home 做成另一个聊天窗口，而是把它作为所有 Agent 的运行控制面：先显示需要关注的变化，再显示持续运行的状态；需要时，用户可以进入结果、权限或规则层。

03 · Core flow

从一句意图，到长期运行。

01自然语言创建

说出目标、关注范围和提醒偏好。

02转为结构化规则

系统整理执行时间、主题、地域、通知与信息源。

03确认权限边界

开始前检查读取、保存、外部操作和数据保留。

04持续运行与汇总

Home 和 Inbox 只突出值得处理的变化。

05对话修改并预演

应用前查看规则差异和 7 天模拟结果。

04 · Key decisions

五个关键设计决定

HOME控制面，而不是聊天页

Home 首先回答“发生了什么”，再让用户进入某个 Agent 的详情和设置。

PROMPT → RULES让自然语言落到可检查的规则

创建完成后展示结构化摘要，避免用户只凭一句 Prompt 猜测系统理解。

PERMISSION在启动前说清能力边界

明确公开信息读取、兴趣保存、外部操作以及数据保留时长。

ATTENTION通知解释“为什么现在告诉你”

变化、原因与下一步操作出现在同一层，未发生变化的执行自动沉底记录。

SAFE EDIT规则修改先预演，再应用

通过变更前后对比、7 天模拟和可撤回记录，降低自然语言自动化的不确定性。

CREATE WITH AI

一句话创建，但不是一句话交付控制权。

用户描述“每天十点整理游戏行业新闻，只在重要变化时通知”。Orbit 将它转换为清晰的 Agent 草稿：执行时间、兴趣主题、目标区域、通知条件与计划信息源均可见、可修正。

  • 保留自然语言的低门槛
  • 用结构化摘要暴露系统理解
  • 在启动前提供修改入口
FINAL CHECK

权限不是法律说明，而是产品体验的一部分。

启动前将 Agent 能读取什么、会保存什么、不会代替用户执行什么，以及数据保留多久放在同一个确认界面。用户可以在设置中随时修改或撤回。

HOME

先给结论，再给运行状态。

首页顶部先汇总“需要确认的变化”，下方才是持续运行的 Agent。航空券、行业信息和职位监测使用不同的信息密度，但共享状态、变化、下一步操作和设置入口。

DAILY BRIEF

日报不是新闻堆叠，而是有理由的选择。

每日行业信息从 24 个来源中选择三项变化，并说明它为什么与用户的兴趣有关。轻量反馈会影响下一次选题，让个性化形成可理解的闭环。

AGENT INBOX

把执行记录与需要行动的通知分开。

Inbox 首先展示需要立即确认的结果，其次是今日摘要，最后才是“已检查但无变化”的后台记录。每条通知都会说明触发原因。

EDIT WITH AI

规则修改需要预期，而不只是确认按钮。

用户用对话提出新的通知限制后，Orbit 显示三项具体变更，并用过去七天的数据模拟通知次数、紧急通知和可能遗漏的重要结果。确认后仍可从历史记录恢复。

好的 Agent 体验，不是让自动化消失，而是让人始终知道它正在如何代表自己行动。ORBIT · DESIGN PRINCIPLE
05 · Reflection

验证计划与下一步

下一轮需要验证

  • 用户能否区分“执行频率”和“通知频率”
  • 权限确认是否足够清楚，同时不过度制造负担
  • 7 天模拟能否真正提高修改规则时的信心
  • Home 与 Inbox 的信息分工是否符合用户预期

当前项目边界

目前是个人完成的高保真产品概念与交互原型，尚未包装为已经上线的真实服务。下一步将通过 5–8 位目标用户的任务测试，验证理解、控制感与通知负担，再继续完善 Agent 模板、异常状态和跨 Agent 协作。
